## 1. 何を比較するかの問題提起(構成案)

小規模なコーポレートサイト(数ページ〜十数ページ、更新頻度は月数回程度)を新規に作るとき、
「とりあえずCMSを入れる」が定石になりがちだが、CMSが本来担っている責務を分解すると、
実は更新頻度・更新者のスキルセット次第で不要になるケースがある、という問題提起から始める。
「WordPressを使うか使わないか」の二択ではなく、CMSが担う責務(コンテンツ編集UI・入稿フロー・
プレビュー・公開反映)をそれぞれ独立した意思決定として切り出す視点を提示する。

## 2. 比較対象の整理(構成案)

以下の3パターンを、責務ごとの表で整理する:

- パターンA: WordPress(管理画面 + DB + テーマ)
- パターンB: ヘッドレスCMS(microCMS / Contentful 等) + 静的フロント
- パターンC: CMSなし(Markdown + Next.js の static export、更新はPRベース)

比較軸は「更新者に必要なスキル」「更新の反映速度」「運用コスト(セキュリティ対応・課金)」
「非エンジニアが自走できるか」の4点を予定。

## 3. 検証手順(Day 2 で実装)

パターンB・Cについて、同一コンテンツ(ダミーの施工事例ページ相当の汎用サンプル)を
最小構成で作り、更新〜反映までの手順を実際に手を動かして比較する。
Next.js の static export 構成を軸に、コンテンツ更新の運用フローをコードで示す予定。

## 4. 結果と考察(構成案)

各パターンの向き不向きを、更新頻度・更新者のリテラシー・予算の3軸でマトリクス化し、
「CMSが必要な条件」を逆算する形でまとめる。Day 2 の実装結果を踏まえて具体的な数値
(ビルド時間・デプロイまでの手順数等、実測できるもの)を入れる。

## 5. データアナリスト視点(構成案)

CMSの要否判断を「責務ごとに分解して意思決定する」アプローチは、データ基盤の要否を
判断する時の考え方(集計をExcelでやるかBIツールを入れるか等)と構造が近い、という
視点を2〜3文で自然に織り込む予定。
